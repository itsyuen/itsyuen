# AGENTS.md

This repository is the top-level professional map for Peter I-Tsyuen Chang's research, teaching, engineering, and work-system ontology. It is not the primary home for substantive project code or large working artifacts.

## Start here

Read these before making structural changes:

1. `README.md` — front door and current high-level map.
2. `docs/ontology.md` — intellectual ownership, research worlds, infrastructure, teaching, and project boundaries.
3. `docs/todoist.md` — Outcome → Milestone → Action logic and the Run 1 → Run 2 → Run 3 working method.
4. `docs/artifact-placement.md` — authoritative editable homes, supporting data, collaboration copies, and backups.
5. `docs/nas-consolidation.md` — historical/current NAS record; treat it as evidence, not as an execution plan.

## Working rules

- Follow **primary intention** when deciding intellectual ownership.
- Do not classify artifacts by file extension alone.
- Prefer one authoritative editable home for each artifact.
- Preserve useful history before restructuring it.
- Apply changes to current/active work first; do not require a complete historical migration.
- In Run 1, recover task intention and associated artifacts before reorganizing either.
- Let repeated real artifact-placement cases reveal future NAS, cloud, Git, local, `SSCLdataRe`, and `TemporaryDataSSCL` roles and boundaries.
- Treat `freeze_file` and `future_outcome` as provisional working annotations, not permanent ontology categories.
- Do not turn NAS/cloud cleanup into a separate top-down redesign unless explicitly requested.
- Keep edits narrow and integrate upward: clarify, merge, rename, split, or relocate only when the existing ontology and evidence justify it.

## Repository boundaries

- `learning` owns personal technical exploration and capability gaps.
- `working` owns intended research/engineering Outcomes, implementation, and evidence.
- `teaching` owns stabilized material curated for a defined subject, audience, and level.
- This `itsyuen` repository owns the public-facing professional map and durable operating guidance.

Do not move private operational details into this public repository unless explicitly intended for publication.

## Change discipline

Before editing, identify what problem the change solves and which existing document should own it. Prefer updating the owning document over creating a new one. Avoid duplicating the same rule across multiple files. Use concise commit messages that describe the conceptual change.
